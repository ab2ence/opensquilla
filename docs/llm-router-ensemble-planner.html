LLM Router + Rule-based Ensemble Planner

本文是阶段一设计草案：以 2026-06-26 v7 Core 输出交接文档为准，直接使用 LLM Router 原始 model_router.v7-core JSON；当用户在 Settings 开启多模型融合时，由确定性的规则匹配层选择 proposer 和 aggregator。 本文档只作为本地设计稿迭代，不涉及上传。

1. 当前决策

LLM Router 输出就是任务画像 不再额外包装 task_profile schema，后续 planner 直接读取原始 model_router.v7-core JSON。
target.tier 是权威字段 训练数据原生字段是 target.tier，serving 若输出 target.level 只作为兼容读取。
模型选择必须是确定性规则 LLM Router 负责理解任务，不直接选择模型名；proposer / aggregator 由规则层从 catalog 选择。
多模型融合由 Settings 开关控制 不开启时走原来的单模型模式；开启时才进入 planner，生成 per-turn ensemble_plan。
Runtime constraints 与 Router JSON 分离 工具、附件、预算、输入长度不从 LLM JSON 里读，由运行时输入提供。
Catalog 是简单模型池 第一版只维护模型、角色、tags、上下文窗口、成本和延迟。模型池里的模型默认可用。
执行计划是 per-turn metadata planner 输出放在当前 turn，不修改全局 llm_ensemble.profiles.default，避免并发污染。

2. 目标架构

现有 api_v7_core 继续作为默认 LLM Router。新增部分只在 Settings 开启多模型融合后生效： 把原始 router JSON、运行时上下文和 Catalog 转成可解释的 proposer / aggregator 计划。

Agent Turn用户输入、历史、附件
LLM Router原始 model_router.v7-core
Settings Toggle多模型融合开关
Runtime Context预算、工具、附件、输入长度
Catalog模型、角色、tags、成本延迟
Tag Mapperrequired_tags / preferred_tags
Rule Planner过滤、排序、互补
Ensemble Plan2-3 proposer + aggregator
Executor复用 provider / EnsembleProvider
边界：关闭开关时保留现有单模型路径；开启开关时 LLM Router 做任务理解，Rule Planner 做融合模型选择，现有 EnsembleProvider 做并行 proposer 与 single-pass synthesis。

3. LLM Router 原始 JSON

planner 直接读取 ctx.metadata.routing_extra.router_raw_output。训练契约里的权威字段是 target.tier；如果 serving 输出 target.level，只在读取层做兼容。 

{
  "schema": "model_router.v7-core",
  "intent": {
    "type": "debug",
    "domain": "software_engineering",
    "language": "mixed"
  },
  "response": {
    "interaction": "direct",
    "shape": "mixed"
  },
  "target": {
    "family": "code",
    "tier": 3,
    "signals": {
      "context": 1,
      "precision": 3,
      "risk": 1,
      "structure": 3
    }
  }
}
读取规则：schema 必须等于 model_router.v7-core。 能力档位读取 target.tier，兼容 serving 的 target.level： tier = target.tier ?? target.level。
字段 训练契约 Planner 用法
intent.type 22 个枚举，例如 agent_execute、debug、extract。 决定任务特化 requirement，例如 code debug、agentic execution、structured extraction。
intent.domain 14 个业务/知识领域。 只做辅助信号；不要把 domain 当作模型能力族。
response.shape plain_text、structured_text、json、table、code、mixed。 决定结构化输出、代码输出、表格输出等 requirement。
response.interaction direct、clarify_required、safe_completion。 safe_completion 先交给 Policy Engine；planner 不替代安全策略。
target.family 10 个主瓶颈能力族。 planner 的主路由依据。
target.tier 整数 1..4，训练数据没有 5。 在多模型融合开启时，决定 proposer 数量和融合强度。
target.signals context、precision、structure、risk 均为整数信号。 作为门槛和保守升级依据，不做线性魔法权重。
禁止期待模型输出：tools、freshness、fallback、 secondary、constraints、model_name、provider、 cost、latency、evidence、explanation、answer。 这些字段由运行时和 catalog 提供，不属于 LLM Router 原始 JSON。

4. Planner 输入分工

Router JSON

任务理解

  • target.family
  • target.tier
  • target.signals
  • intent.type / response.shape
Runtime

运行时上下文

  • 工具、视觉、附件需求
  • 估算输入 token
  • 本次调用预算
Catalog

模型池

  • 基础字段：模型、provider、角色
  • 角色：proposer / aggregator
  • 能力标签：按 Router 字段映射
  • 运行字段：成本、延迟、上下文窗口
原则：不要把运行时字段塞回 LLM Router schema，也不要让 LLM Router 输出模型名。

5. Tagged Model Catalog：Planner 的候选模型池

第一版 Catalog 不做复杂模型画像，也不写能力等级。它只是一个带标签的候选模型列表。 Rule Planner 把 LLM Router 的 target.family、target.tier、 intent.type、response.shape 映射成 required_tags 和 preferred_tags，再用这些 tag 去匹配模型。

字段 类型 / 取值 说明
catalog_version string，例如 2026-07-01.1 用于日志回放。planner 必须记录本次选择使用的 catalog 版本。
models array 当前可被 planner 考虑的模型列表。
model_id string 模型调用 ID，例如 OpenRouter 的 provider/model。planner 不在规则里硬编码具体模型名。
provider string，例如 openrouter 实际调用 provider。第一版可以只支持当前 provider。
roles array of proposer / aggregator 模型可承担的 ensemble 角色。proposer 负责候选答案，aggregator 负责阅读候选并融合。
tags array of string 模型能力标签。planner 只做 tag 匹配，不解释 tag 内部强弱。
context_window integer 上下文窗口 token 数。用于长上下文硬过滤。
cost low / medium / high / premium 成本桶。同等匹配时用于排序，不参与能力判断。
latency low / medium / high 延迟桶。同等匹配时用于排序，不参与能力判断。
第一版 tag 对应 Router 字段 用途
agentic target.family=agentic 或 intent.type=agent_execute agent loop、规划执行、多步任务。
tool_use runtime 表示本 turn 需要工具调用 工具调用和参数生成，不从 Router JSON 读取。
code target.family=code、intent.type=debug / code_review 代码生成、调试、修复、审查。
long_context target.family=document 或 target.signals.context>=3 长上下文理解、压缩和跨段综合。
structured_output response.shape=json/table 或 target.signals.structure=5 严格 JSON、表格、结构化文本输出。
reasoning target.family=reasoning、precision>=4、risk>=4 判断、验证、发现错误和处理高精度任务。
vision target.family=visual 或附件包含图像 图像理解、多模态输入。
math target.family=math 或 intent.type=math_solve 数学推理和计算。
instruction_following response.shape 有强格式要求，或 aggregator 角色 遵守输出格式、约束和最终表达。
联动方式：Router JSON 不直接选模型，而是映射成 required_tags 和 preferred_tags。模型必须包含 required tags；preferred tags 命中越多越靠前。 
{
  "router_raw_output": {
    "intent": {"type": "debug", "domain": "software_engineering"},
    "response": {"shape": "mixed", "interaction": "direct"},
    "target": {
      "family": "code",
      "tier": 3,
      "signals": {"context": 1, "precision": 3, "structure": 3, "risk": 1}
    }
  },
  "planner_match": {
    "proposer_count": 2,
    "required_tags": ["code"],
    "preferred_tags": ["reasoning", "structured_output"],
    "aggregator_preferred_tags": ["reasoning", "instruction_following", "structured_output"],
    "reason_codes": [
      "target.family=code",
      "target.tier=3",
      "intent.type=debug",
      "response.shape=mixed"
    ]
  }
}

7. Planner 流程

Step 1

硬过滤

  • 角色：proposer / aggregator
  • 上下文窗口足够
  • runtime 需要工具或视觉时，模型必须包含对应 tag
  • 成本、延迟满足本次预算偏好
Step 2

生成 tags

  • target.family 决定 required_tags
  • target.tier 决定默认执行强度
  • intent.type 补充 preferred_tags
  • response.shape 补充结构化输出 tag
  • target.signals 触发长上下文、推理、安全保守策略
Step 3

可解释排序

  • 先满足 required tags
  • 再看 preferred tags 命中数
  • 再看角色适配、成本和延迟
  • 最后处理成本、延迟和互补性

8. Router 字段到 Tags 的映射规则

这一节只定义 Router JSON 如何映射到 required_tags 和 preferred_tags。 这些 tags 直接和 Catalog 里的 tags 字段匹配，不再引入新的 requirement 对象。

Router / Runtime 条件 Required Tags Preferred Tags
target.family=agentic 或 intent.type=agent_execute agentic tool_use, reasoning
target.family=code code reasoning, structured_output
target.family=document long_context reasoning, instruction_following
target.family=reasoning reasoning instruction_following
target.family=visual 或图像附件 vision reasoning
target.family=math 或 intent.type=math_solve math reasoning
response.shape=json/table 或 target.signals.structure=5 structured_output instruction_following
target.signals.context>=3 long_context reasoning
target.signals.precision>=4 reasoning, instruction_following
runtime 需要工具调用 tool_use agentic
安全边界：response.interaction=safe_completion 或 target.signals.risk>=4 不由 planner 替代安全策略。Policy Engine 先处理；planner 只在允许执行时选择更稳的模型。

9. Proposer 选择

Proposer 负责生成候选答案。只有 Settings 开启多模型融合时才执行本节规则；关闭时不进入 planner， 直接沿用原来的单模型路径。

Proposer 数量

开启融合后，target.tier 只决定 proposer 数量，不再决定是否使用单模型。

条件数量
target.tier=12 proposers + 1 aggregator
target.tier=22 proposers + 1 aggregator
target.tier=3默认 2 proposers + 1 aggregator；repair、agentic、高 precision/context 可到 3
target.tier=4默认 3 proposers + 1 aggregator；safe_completion 先经过 Policy Engine

选择规则

  • roles 包含 proposer。
  • context_window 足够容纳当前输入。
  • 必须包含全部 required_tags。
  • preferred_tags 命中越多越靠前。
  • 需要多个 proposer 时，后续 proposer 优先补齐尚未覆盖的 preferred tag。
  • 同分时按 cost、latency 排序。

10. Aggregator 选择

Aggregator 负责阅读 proposer 候选并输出最终答案。它不一定是最会做原任务的模型，但必须适合综合、判断和遵循格式。

基本规则

  • roles 包含 aggregator。
  • 上下文窗口能容纳原始输入和 proposer outputs

偏好规则

  • 优先包含 reasoning。
  • 优先包含 instruction_following。
  • response.shape=json/table 时优先包含 structured_output。
  • 输入或候选很长时优先包含 long_context。
  • target.family=code 时可偏好包含 code，但不强制。

12. 接入点：per-turn ensemble_plan

ensemble_plan 是每个 turn 的动态融合计划。它不是全局配置，也不是 Router JSON 的一部分。 Settings 关闭多模型融合时不生成它，runtime 继续走原来的单模型路径；Settings 开启后才生成它，并进入融合执行阶段。

apply_squilla_router只负责 LLM Router / tier / routing_extra
Settings检查多模型融合开关
apply_ensemble_planner开启时读取 router_raw_output 和 catalog
ctx.metadata开启时写入 ensemble_plan
runtime读取 ensemble_plan
provider构造 EnsembleProvider

apply_squilla_router

继续负责当前 LLM Router 逻辑：调用 api_v7_core，写入 routing_extra.router_raw_output、routed_tier 和基础路由元数据。

apply_ensemble_planner

新增独立 step，只在 Settings 开启多模型融合时执行。读取 routing_extra.router_raw_output，按 tag 规则查询 Catalog，生成当前 turn 的 ctx.metadata["ensemble_plan"]。

runtime

不重新理解 Router JSON。Settings 关闭时沿用原来的单模型 provider；Settings 开启且存在 ensemble_plan 时，构造 EnsembleProvider。

Ensemble Plan

{
  "schema": "opensquilla.ensemble_plan.v1",
  "mode": "ensemble_single_pass",
  "proposers": [
    {"provider": "openrouter", "model": "provider/model-a"},
    {"provider": "openrouter", "model": "provider/model-b"}
  ],
  "aggregator": {
    "provider": "openrouter",
    "model": "provider/model-c"
  },
  "strategy": "single_pass_synthesis"
}
不要做：不要每个 turn 修改全局 config.llm_ensemble.profiles.default。 ensemble_plan 是 Settings 开启后的 per-turn decision，必须只存在当前 turn 的 metadata 中。

13. 待讨论问题

第一版模型池放哪些模型，是否只覆盖当前默认 OpenRouter 候选池？ 当前答案：只覆盖当前默认 OpenRouter 候选池，先不引入多 provider 差异。
每个模型的 tags 先由谁维护，第一版是否手写即可？ 当前答案：第一版先手写维护，后续再考虑从评测或线上数据更新。
target.tier 到 proposer 数量的规则是否就按当前表执行？ 当前答案：确定，第一版就按第 9 节当前表执行。
多模型融合是否默认开启，还是由 Settings 按钮控制？ 当前答案：由 Settings 按钮控制。不开启时走原来的单模型模式；开启时走融合。
Aggregator 的资格是否只由 roles 里的 aggregator 决定？ 当前答案：是。tags 只用于排序偏好，不用于定义 aggregator 资格。
LLM Router 后处理得到的 thinking_mode 是否影响 ensemble member 的 thinking 设置？ 当前答案：跟随使用。第一版让 proposer 和 aggregator 的 thinking 设置跟随当前 turn 的 thinking_mode。
